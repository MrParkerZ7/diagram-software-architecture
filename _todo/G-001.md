## Why / vision

The owner asked, verbatim: **"write diagram micro frontend foreach CSR,SPA,MPA,SSR,SSG,ISR,RSC"**, with a link to the
owner's own chat "Frontend architecture patterns" (read 2026-11-15; the chat's own date is not known).

That chat separates three concerns that mix freely: rendering (where the HTML is produced), the BFF (where data is
combined) and caching (where results are reused). It names micro-frontends as a team-structure choice (Module
Federation, single-spa) but never says how micro-frontends are composed under each rendering approach. Each slot's
`_origins.md` cites the chat by its title and the date it was read, marked private, with no link: the chat is not
public and this repo is.

Seven diagrams drawn from one frame answer that side by side. The reader sees the same page seven times and watches one
thing move, the **composition point**:
- CSR: in the browser, at first load;
- SPA: in the browser, at every route change;
- MPA: at the edge, per request;
- SSR: on the origin, per request;
- SSG: at build time;
- ISR: on the origin, at regeneration time;
- RSC: on the origin, per request, inside one React tree.

The repo also exists to improve the diagram skill by using it: seven same-frame diagrams are a hard, comparable test of
the 3-diagram kit, its two gates and the library layout, and the lessons go back into the prompt master (T-008).

**Decisions settled (2026-11-15, todo-new planner; panel round 1 applied):**
- **D1 Frame.** One ROAD (cloud-architecture type) page.
  - Four request-tier columns, left to right: Browser, Edge, Origin, Backend. A Build-time band runs under Edge and Origin.
  - A fixed set of nodes is placed the same way in all seven diagrams (an example shop with three teams: A Catalog, B Cart, C Account).
  - **Form (the owner, 2026-11-16):** every node is an icon with its name as a caption, and the numbered arrows carry
    the workflow; no node is a text card (*"the diagram workflow should be bease with icon arrow workflow relation"*;
    the prompt master's architecture rule, and T-001's ⚠ contract-change). An `App shell` group holds the runtime
    loader and the client router.
  - **Classes:** team = colour class, said by the caption's tint, all cool. A node an approach does not use stays in
    place, muted (the icon and its caption faded), and is never removed.
  - **The composition point (pivot)** is marked by the one amber caption on the page (#FFD54F). Position and size stay
    fixed so the seven pages compare.
  - **Cables:** every run-time cable joins adjacent columns, stays inside one container as one straight segment, or runs
    in a street, a gutter or the east lane outside every column; build cables rise from the band. Every cable has
    explicit ports. **Every bend sits in free space, never inside a rectangle**, a cable's own column, group or band
    included (`check_layout.py` WAYPOINT-IN, hard), and no cable leaves and re-enters its own container (RE-ENTRY).
  - **Numbering:** the steps of the flow a page draws are numbered in order, and numbered build steps come first. An
    unnumbered cable stands outside that order: a build or deploy link, a standing link, or a separate trigger such as
    ISR's CMS publish.
  - **Furniture:** page furniture is `kitExempt=1`.
  - **Glyphs** come only from the 3-diagram kit's `CLAY_DEMO`, never from `mxgraph.*` libraries. **Superseded 2026-11-17 (T-001):** the icons are a generic shape of `PROMPT_ICON.md` first, then a crafted icon of the prompt master's craft kit; the clay glyphs are not used.

## Risks

- **Thin practice in some technologies.** Runtime federation of React server components is experimental. `nextjs-mf` is being retired and never supported the App Router. Where server-side composition falls back on a slow fragment varies by tool. Mitigation: each page states only what its sources say, cites them in `_origins.md`, and marks the rest experimental or lists it in spec section 8. T-007 stays on Opus.
- **The frame proved on one diagram.** Mitigation: T-001's dry run builds all seven full pages before the frame is frozen.
- **Parallel builders on shared files.** All six touch the library README `## Storage` table, and all import the frame. Mitigation: fixed slot numbers, each row inserted in number order and committed through the Row-only README commit (T-001 step 2), commits by exact pathspec, and the frame frozen (a needed change becomes a new ticket, never an edit inside T-002 to T-007).
- **One drive's half-done builder blocking every session.** The prompt master's `guard-spec-sync.mjs` checks this repo's whole working tree: a builder with no unit spec beside it blocks every session's Stop. Mitigation: each ticket writes its unit spec before its builder and commits both together.
- **Two specs deviated from.** LIBRARY.md section 2a ("a builder writes only inside its own workspace") and `diagram-generate.md`'s output path. Mitigation: T-008 records both, under the master's `@@@` loop.
- **Render fidelity.** The headless viewer draws inline kit stencils but not `mxgraph.*` library shapes. Mitigation: the frame uses kit glyphs only. **Superseded 2026-11-17:** a probe showed the viewer draws `mxgraph.*` shapes and image cells too.
- **Public repo.** No absolute machine path, user name, e-mail or profile may enter any committed file. Mitigation:
  - the kit is found through the `DIAGRAM_KIT` environment variable;
  - the render helper finds the browser and the viewer through environment variables at run time;
  - before every commit, the staged text passes the pre-commit leak check, `git diff --cached -U0 --no-color -- <pathspec> | grep -E '^\+' | grep -vE '^\+\+\+ ' | grep -nE '(^|[^A-Za-z])[A-Za-z]:[\\/]|/Users/|/home/|AppData'`, and the commit message passes `grep -nE '(^|[^A-Za-z])[A-Za-z]:[\\/]|/Users/|/home/|AppData' <msg>` (a hit stops the commit), and every ticket's Done when searches its committed files again afterwards.
