## Context

The second of G-001's seven diagrams. The CSR diagram (T-001) shows the **first load**. This one shows what happens
**after** it, inside one long-lived page:
- a link click is caught by the shell's client router, which unmounts the current team UI and mounts the one that owns
  the new route, with no page load;
- team UIs talk through an event bus, never by importing each other;
- they share one copy of React.

The composition point is the **client router** (the browser, at every route change). The chat groups CSR and SPA;
G-001's D3 splits them into the first-load view and the navigation view. Labels are in English (Q1).

### Content
- **Title:** `Micro-frontends with SPA: single-page application (navigation after the first load)`.
- **S1 (HTML):** `In the browser, at every route change. The one HTML document (a near-empty index.html from the CDN) is fetched once; after that no HTML is requested again.`
- **S2 (composed):** `In the browser, at every route change: the shell's client router unmounts the current team UI and mounts the team UI that owns the new route, inside the same page (single-spa activity functions, or lazy routes loading Module Federation remotes).`
- **S3 (trade-off):** `Navigation needs no page reload and teams still deploy separately. But every team UI lives in one long-lived page: memory, global CSS and event listeners leak between them unless each cleans up on unmount, and shared singletons (one React) must match.`

**Sources for `_origins.md`** (verified 2026-11-15):
- The owner's chat, cited as the rule says: CSR and SPA load the JavaScript once and render everything in the browser;
  an SPA is smooth to use.
- single-spa documentation (single-spa.js.org/docs/building-applications): an application is loaded (its code fetched
  from the server and run, the first time its activity function returns true), then bootstrapped, then mounted, which
  is why the Cart UI's bundle (step 2) comes before its mount (step 3);
- single-spa documentation (single-spa.js.org): each registered application exports `bootstrap`, `mount` and `unmount`;
  an activity function decides from the URL which applications are active; `unmount` must clean up the DOM, event
  listeners, leaked memory and globals.
- martinfowler.com/articles/micro-frontends.html: routes as the contract between micro-frontends; custom events let them
  communicate indirectly.
- Module Federation documentation (module-federation.io): shared singletons. Check the current wording when citing it.
