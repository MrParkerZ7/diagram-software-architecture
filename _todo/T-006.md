## Context

The sixth of G-001's seven diagrams. ISR is SSG that can regenerate pages after the build without rebuilding the whole
site. The behaviour, from the Next.js documentation:
- **At build:** the known pages are prerendered.
- **A page not yet built** is rendered on demand while its request waits (MISS).
- **Time-based:** after the revalidate window, the next request still gets the cached, stale page, and regeneration
  starts in the background (STALE). Once it succeeds, the new page replaces the cached one.
- **On demand:** `revalidatePath` invalidates a path; `revalidateTag` invalidates tagged data across all pages that use
  the tag, and with the `max` profile the next request is still served stale while it revalidates.

With micro-frontends, the composition happens **on the origin at regeneration time**: the page composer re-renders the
page from each team's current fragment, and the result is cached and served to everyone. Because every page holds all
three teams' fragments, a team deploy revalidates **every page that holds its fragment**, through a per-team cache tag,
not only the paths it owns. The composition point is the **page composer acting as regenerator**. Labels are in English
(Q1).

### Content
- **Title:** `Micro-frontends with ISR: incremental static regeneration (composed on regeneration)`.
- **S1 (HTML):** `At build time for the known pages; then on the origin when a page is first requested or regenerated. Every other request gets the cached copy.`
- **S2 (composed):** `On the origin, at regeneration time: after the revalidate window (the next request still gets the stale page while a new one is built in the background), or on demand: a team deploy or a CMS publish (revalidatePath or revalidateTag) marks the page stale, and the next request regenerates it. The composer re-renders the page from each team's current fragment, and the cache serves it to everyone.`
- **S3 (trade-off):** `Static speed without a full-site rebuild, and a team deploy reaches users by revalidating every page that holds its fragment (a per-team cache tag, e.g. revalidateTag('team-b', 'max')). But the first request after the window (or after a revalidation with max) still gets the stale page, however old, and a failed regeneration keeps serving it; and where the ISR cache sits in each origin instance (the self-hosted default), several instances need a shared cache handler or a revalidation reaches only one of them.`

**Sources for `_origins.md`** (read 2026-11-15):
- **nextjs.org/docs/app/guides/incremental-static-regeneration** (page dated 2026-10-15):
  - during `next build` a page is prerendered for each known path; a page not yet built is generated on demand (MISS:
    not in cache, rendered fresh);
  - after the window, the next request still returns the cached stale page, and regeneration begins in the background;
  - if an error is thrown while revalidating, the last successfully generated data continues to be served from the
    cache (this sources S3's "a failed regeneration keeps serving it");
  - `revalidatePath` invalidates, and regeneration happens on the next request (App Router); the Pages Router has
    `res.revalidate` for eager regeneration;
  - ISR is not supported with a static export, and runs only on the Node.js runtime;
  - with several instances the default file-system cache is per instance, and on-demand revalidation reaches only the
    instance that receives the call unless a shared cache handler is configured;
  - the `x-nextjs-cache` header values are HIT, STALE, MISS and REVALIDATED.
- **nextjs.org/docs/app/api-reference/functions/revalidateTag** (page dated 2026-08-25): it "invalidates data with
  specific tags across all pages that use those tags"; with `profile="max"`, "requests are always served stale content
  while the revalidation runs" (this sources S3's "or after a revalidation with max"); a revalidation is triggered by
  the next request, not by the call (this sources S2's "the next request regenerates it"); it can be called in Server
  Functions and Route Handlers.
- The owner's chat, cited as the rule says: ISR regenerates some pages periodically without rebuilding the whole site.
