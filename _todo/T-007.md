## Context

The last of G-001's seven diagrams. With React Server Components, components are split into server components and
client components (marked `"use client"`). Per the React documentation:
- server components run on the server, per request or at build;
- their code is never sent to the browser;
- `Suspense` boundaries stream the output progressively.

With micro-frontends, the composition happens **on the origin, per request, inside one React tree**: the shell's server
components render each team's components, and each team's section is wrapped in its own `Suspense` boundary, so it
streams in when ready. In the browser, only the client components hydrate. This view draws **dynamic rendering**; server
components can also be prerendered at build time.

**The honest part, which this page must state.** Today, teams integrate RSC components through **build-time packages**
in one server app (stable), or split **by route into separate apps** (Next.js Multi-Zones, with hard navigation between
zones). Federating server components at run time is **experimental**:
- Module Federation 2.0 lists RSC under "what's next";
- the community Next.js plugin (`nextjs-mf`) is being retired and never supported the App Router.

The page draws the build-time package model. The composition point is the **page composer acting as the React server
tree**. Labels are in English (Q1).
